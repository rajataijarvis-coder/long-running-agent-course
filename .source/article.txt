Building a Week-Long Running Agentic System
Durability is an engineering property, not a model capability

Most AI agents are a single loop that dies the moment the process restarts, the context window fills up, or one API call fails. That is fine for a quick chat, but it falls apart on long horizon tasks that run for days or weeks. In this blog we build an agent that keeps running across that whole stretch. It plans its own work, builds and tests real software, and learns from its failures to improve itself for the next run. The model does not need to be any smarter for this. The system around it does the heavy lifting.

Week long running agentic system (Created by Fareed Khan)

Here is the shape of the whole thing before we build it. A human can approve and steer through durable signals. A durable control plane schedules the work. An agent team does the work, with one lead engineer and a few helpers. The real state lives in git plus a tiered memory, and a deterministic verifier is the only thing allowed to call a piece of work done.

I wanted to see how far we can push the other direction.
What if we treat long horizon autonomy as an engineering problem instead of a model capability?
The model thinks in short bursts, and the system runs for weeks by doing three boring things very well. It keeps the real state outside the model, it journals every step, and it verifies progress with real tests.

Throughout this blog I will follow one concrete task so the ideas stay grounded. The task is to build a small Python language server (an LSP server) from scratch, and it takes the system about a week. The trace below is a representative run of that task, and by the end of the blog you will understand every line of it.

2026-06-02T08:44:51.880Z INFO  mission.complete items=14/14 cycles=615 head=9d8c7b6 status=DONE
2026-06-02T08:44:51.900Z INFO  governor.final cum_usd=178.60 ceiling=400.00 crashes_survived=1
                               loop_trips=1 reviewer_blocking=2 scope_cuts=1 skills_learned=2

That single task survived a host reboot, tripped a loop detector once, got blocked twice by an independent reviewer, cut its own scope when it over planned, and learned two reusable skills along the way. All for 178 dollars and 60 cents of tokens against a 400 dollar ceiling. Let us build the system that produced that line, one piece at a time.

The model layer is pluggable, so you can run the whole system for zero dollars. A local Ollama model or a free tier cloud model costs nothing, and a `stub` model is used for tests. You only pay for tokens when you point it at a paid API like Claude. Here is the quickstart:

# install (this provisions Python 3.12 for you)
uv sync
uv run lra version
uv run lra config        # show the resolved config, with secrets redacted

# run a mission locally, no servers needed (uses the stub model at $0)
uv run lra mission --task \"Create a hello.py that prints hello and a test for it\" \\
                   --workdir .lra/workspaces/demo

That lra mission command plans the task into a checklist and then works each item until it is verified. In the commands and logs you will see this called a mission, as in lra mission, which is just the system’s word for one run on one task. Everything it does is real git history, so you can inspect the work afterwards with git -C .lra/workspaces/demo log --oneline. Now let us understand why the system is built the way it is.

The Core Idea: Assume Interruption

Before any code, we need the one idea that everything else hangs on. If an agent has to run for a week, then over that week it will be interrupted. The machine will reboot, the API will rate limit, the context window will overflow, the worker process will get killed by a deploy. Interruption is not an edge case here. It is the normal case. So we design for it from the start, and the rule we follow is simple: assume interruption.

The Context Window Is a Lossy Cache

The most common mistake is to treat the model’s context window as the agent’s memory. It is not. The context window is a small, lossy cache. It holds a few hundred thousand tokens at most, it gets summarized or truncated when it fills, and it vanishes entirely when the process restarts. If our agent’s understanding of “where am I in this task” lives only in the context window, then the first interruption erases it.

Press enter or click to view image in full size
The context window is a small lossy cache that vanishes on interruption (Created by Fareed Khan)

So the context window is going to fill up after thousands of turns, and a crash or a reboot will throw it away. When that happens, a naive agent loses all sense of where things stand. It does not know which files it already wrote, which tests already pass, or which design decisions it already made. This is exactly why most long agent runs fall apart. We are going to fix this by moving the real state somewhere that does not disappear.

The Real State Lives Outside the Window

The fix is to keep the real state of the task outside the model, in a place that survives anything. We use a git repository plus a few structured files inside it. The model reads this state at the start of every cycle to catch up, does a small amount of work, and commits the result back. The context window becomes disposable, because the state is never in it.

Press enter or click to view image in full size
The real state lives in git, re-read every cycle and committed back (Created by Fareed Khan)

This is the whole idea in one picture. The real state is a git repo plus a small set of saved state files. The model reads it fresh every cycle, so a brand new model with an empty context window can rebuild full awareness in seconds. Then it commits its results back into the same state. A crash between cycles loses nothing, because the only durable state is the part we already committed. Now let us build that saved state.

The Saved State

The saved state is the set of files that hold everything that matters. It lives in a folder called .lra/ inside the repository we are working on, and it is committed to git alongside the actual code changes. That way, one commit captures both the work and the progress on the work. Let us look at the data first, because the data is the design.

The Checklist

The center of the saved state is a checklist. Each item is one small unit of work, and an item can only be in one of four states. It is todo, in_progress, blocked, or done. The important rule, which we will enforce later, is that an item flips to done only after a real test proves it. Here is the data model, written with Pydantic.

# src/lra/contracts/state.py

ItemStatus = Literal[\"todo\", \"in_progress\", \"blocked\", \"done\"]


class ChecklistItem(BaseModel):
    \"\"\"One mission work-unit; flips to `done` only after deterministic verification.\"\"\"

    id: str
    description: str
    status: ItemStatus = \"todo\"
    # IDs of the checks (tests/lint) that actually proved this item done.
    verified_by: list[str] = Field(default_factory=list)
    depends_on: list[str] = Field(default_factory=list)  # other item ids
    attempts: int = 0                                     # how many tries so far
    notes: str = \"\"
    schema_version: int = 1                               # for safe migrations later

    @property
    def is_open(self) -> bool:
        return self.status in (\"todo\", \"in_progress\", \"blocked\")

Each item carries its own dependency list and an attempt counter. The verified_by field is an audit trail. It records the names of the checks that proved the item done, so later we can answer “how do we know this works?” with a concrete answer instead of a guess. Now the checklist itself is just an ordered list of these items, plus one very important method.

class Checklist(BaseModel):
    items: list[ChecklistItem] = Field(default_factory=list)
    schema_version: int = 1

    def next_actionable(self) -> ChecklistItem | None:
        \"\"\"Return the first open item whose dependencies are all done, else None.\"\"\"
        done = {i.id for i in self.items if i.status == \"done\"}
        for item in self.items:
            if item.is_open and all(dep in done for dep in item.depends_on):
                return item
        return None

    @property
    def all_done(self) -> bool:
        return bool(self.items) and all(i.status == \"done\" for i in self.items)

The next_actionable method is how the agent always knows what to do next. It walks the list and returns the first open item whose dependencies are all complete. This is what lets a fresh agent, with no memory, pick up exactly where the last one left off. It does not need to remember anything. It just asks the checklist.

Decisions and Events

A checklist tells you what is left, but it does not tell you why earlier choices were made, and it does not give you a blow by blow history. For those, we keep two append-only logs next to the checklist. One is for decisions, and one is for events.

class DecisionRecord(BaseModel):
    \"\"\"A durable, never-compacted record of an implicit design decision (anti-drift).\"\"\"

    decision: str               # e.g. \"use a synchronous read loop, not asyncio\"
    rationale: str
    alternatives_rejected: str = \"\"
    affected: list[str] = Field(default_factory=list)   # item ids this touches
    cycle_id: str = \"\"


class EventRecord(BaseModel):
    \"\"\"One entry in the append-only episodic event log.\"\"\"

    kind: str                   # \"cycle\", \"tool_call\", \"verification\", ...
    cycle_id: str = \"\"
    payload: dict[str, object] = Field(default_factory=dict)
    # Pointer to a large blob in the object store, to keep the log compact.
    payload_ref: str | None = None

The decision log matters more than it looks. When the context window gets compacted, the first things to get dropped are the small implicit decisions, like “we chose to read bytes directly instead of using input()\". Those are exactly the decisions that cause drift later, when a future cycle quietly contradicts a past one. By writing them to an append-only file that is never compacted, we can always check new work against old decisions.

Decisions and events are append-only logs that never get compacted away (Created by Fareed Khan)
Reading Where Things Stand

Now the key operation. At the start of every single cycle, the agent rebuilds its full awareness from these files plus the git log. This is the “assume interruption” rule turned into a method. Here is the read path, from the GitMissionAnchor class.

# src/lra/state/mission_anchor.py

def _read_sync(self) -> SituationSnapshot:
    checklist = self._read_checklist()
    progress = \"\"
    progress_path = self._path(PROGRESS_FILE)
    if progress_path.exists():
        progress = progress_path.read_text(encoding=\"utf-8\")

    # The active item is whatever is in_progress, else the next actionable one.
    active = next((i for i in checklist.items if i.status == \"in_progress\"), None)
    if active is None:
        active = checklist.next_actionable()

    return SituationSnapshot(
        head_sha=git_ops.head_sha(self.workdir),
        recent_commits=git_ops.log_oneline(self.workdir, 10),
        progress_summary=progress,
        open_items=[i for i in checklist.items if i.is_open],
        last_decisions=self._read_recent_decisions(5),
        active_item=active,
        is_complete=checklist.all_done,
    )

Read that method slowly, because it is the core of the whole system. It opens the checklist file, reads the progress narrative, finds the active item, pulls the last ten git commits and the last five decisions, and packs it all into one SituationSnapshot. This runs in milliseconds, and it works for a brand new process that has never seen this task before. That is what makes a crash a non event. The next worker just reads the snapshot and continues.

The current state is rebuilt from git and the state files in milliseconds (Created by Fareed Khan)
Committing a Checkpoint

The other half is writing. When a cycle finishes, we write the updated files and commit them in a single atomic git commit. If the commit succeeds, the real state advanced. If anything crashed before the commit, the real state simply did not advance, and the next cycle retries the same item. There is no half-done state.

def _commit_sync(self, checkpoint: Checkpoint) -> str:
    self.anchor.mkdir(parents=True, exist_ok=True)
    self._write_checklist(checkpoint.checklist)              # checklist.json
    if checkpoint.progress_summary:
        self._path(PROGRESS_FILE).write_text(checkpoint.progress_summary, encoding=\"utf-8\")
    if checkpoint.decisions:                                 # append, never overwrite
        with self._path(DECISIONS_FILE).open(\"a\", encoding=\"utf-8\") as fh:
            for decision in checkpoint.decisions:
                fh.write(decision.model_dump_json() + \"\
\")
    if checkpoint.events:                                    # append, never overwrite
        with self._path(EVENTS_FILE).open(\"a\", encoding=\"utf-8\") as fh:
            for event in checkpoint.events:
                fh.write(event.model_dump_json() + \"\
\")
    message = checkpoint.commit_message or f\"lra: checkpoint {checkpoint.cycle_id}\"
    return git_ops.commit_all(self.workdir, message)         # git add -A && git commit

Notice the decisions and events are appended, not overwritten, while the checklist is rewritten in full. The whole thing ends with one git commit. Because the commit message is deterministic and readable, the git history itself becomes a human readable progress report. Here is what the history looks like after a small three item task finishes.

#### OUTPUT ####

b3c4d5e lra: complete 02 (task 2)
a1f2e3d lra: complete 01 (task 1)
0c1d2e3 lra: initialize mission anchor

One commit per finished item, plus the initial commit that created the saved state. You can read the entire task from the git log without any special tools. This is the benefit of putting the real state in git. Now we have a place to store progress. Next we need the loop that actually makes that progress.

The Agent Cycle

We have a place to store the real state. Now we need the loop that reads it, does a little work, and writes it back. I call this one unit of work a cycle. A cycle is deliberately small. It works on one checklist item, runs the model for a few turns, verifies the result, and commits. Keeping the unit small is what makes the system resilient, because the most we can ever lose to a crash is a single unfinished cycle.

Think, Act, Verify, Checkpoint

Every cycle follows the same four steps. It reads where things stand from git, it acts by running the model and its tools, it verifies the result with real checks, and it checkpoints the outcome back to git. Then it repeats.

Press enter or click to view image in full size
One cycle: read the state, act with tools, verify, then checkpoint (Created by Fareed Khan)

Here is the top of the cycle, from the AgentLoop class. The first thing it does is read the snapshot, and if the task is already complete, it returns immediately. That early return is what makes the whole loop idempotent.

# src/lra/agent/loop.py

async def run_cycle(self, *, ctx, mission_id, cycle_id, anchor_text, checks=None):
    checks = checks or []
    snapshot = await self._anchor.read_situational_awareness()
    # Idempotent guard: if there is nothing left to do, this cycle is a no-op.
    if snapshot.is_complete or snapshot.active_item is None:
        return CycleOutcome(
            item_id=None, advanced=False, verified=False,
            is_complete=True, head_sha=snapshot.head_sha, tool_calls=0, turns=0,
        )

    item = snapshot.active_item  # the one thing we will work on this cycle
    messages = build_messages(
        anchor_text=anchor_text, snapshot=snapshot, item=item,
        specs=self._dispatcher.specs(),   # the tools this agent is allowed to use
    )

The cycle picks exactly one item, the active item from the snapshot, and builds a prompt that includes the progress so far, the open items, and the tools it is allowed to call. Notice that it never trusts its own memory for what to work on. It always asks the freshly read snapshot. Now it enters the part where it actually thinks and acts.

The Tool Loop

Inside a cycle, the model and the tools take turns. The model produces either a tool call or a “done” signal. If it is a tool call, we run the tool, feed the result back as an observation, and ask the model again. We repeat this up to a fixed number of turns, so a confused model can never loop forever inside a single cycle.

Press enter or click to view image in full size
The model and tools take turns until the model signals done or the turn cap is hit (Created by Fareed Khan)
tool_calls = 0
for turns in range(1, self._max_turns + 1):
    result = await self._model.complete(messages)     # one real model turn
    if self._ledger is not None:                      # record real token cost
        self._ledger.record(
            cycle_id=cycle_id, usage=result.usage,
            usd=self._model.estimate_cost_usd(result.usage),
        )

    action = parse_action(result.text, result.tool_calls)
    if action.done or action.tool is None:            # the model says it is finished
        messages.append(ModelMessage(role=\"assistant\", content=result.text))
        break

    # Run the requested tool through the safety gate (more on that gate later).
    call = ToolCall(id=f\"{cycle_id}-{turns}\", name=action.tool, arguments=action.arguments)
    tool_result = await self._dispatcher.dispatch(call, ctx)
    tool_calls += 1
    observation = (tool_result.content or tool_result.error or \"\")[:4000]
    messages.append(ModelMessage(role=\"assistant\", content=result.text))
    messages.append(ModelMessage(role=\"user\", content=f\"OBSERVATION ({action.tool}): {observation}\"))

Every model turn records its real token usage into a cost ledger, which we will use later to enforce a budget. The observation we feed back is capped at four thousand characters, so a giant tool output cannot blow up the context. When the model finally signals it is done, we break out and move to verification. Here is one cycle from the real LSP task, where the lead engineer writes the transport file and runs the test.

One model turn, one file written, one test run, and it failed with a timeout. That is a perfectly normal cycle. The work did not pass, so the item will not be marked done. Instead it gets recorded as a failed attempt and the next cycle will try again. This is the system working exactly as designed, and we will follow this particular bug to its conclusion later.

Context Compaction

A single cycle can run many turns, and the message list grows with each tool call and observation. If a cycle explores a lot, that list can get long enough to strain the window. So we compact it. We keep the system prompt and the most recent few turns exactly as they are, and we summarize everything older into one compact note.

Press enter or click to view image in full size
Compaction keeps the system prompt and recent turns, summarizing the older ones (Created by Fareed Khan)
# src/lra/agent/compaction.py

async def compact_messages(*, model, messages, keep_last=4):
    \"\"\"Return system + a summary-of-older-turns + the last `keep_last` turns.\"\"\"
    system = [m for m in messages if m.role == \"system\"][:1]    # never compact this
    body = [m for m in messages if m.role != \"system\"]
    if len(body) <= keep_last:
        return messages                                         # nothing to do yet

    to_summarize = body[:-keep_last]                            # older turns
    recent = body[-keep_last:]                                  # keep these verbatim
    transcript = \"\
\".join(f\"{m.role}: {m.content}\" for m in to_summarize)[:12000]
    result = await model.complete([
        ModelMessage(role=\"system\", content=_SUMMARY_INSTRUCTIONS),
        ModelMessage(role=\"user\", content=transcript),
    ])
    summary = ModelMessage(role=\"user\", content=f\"[compacted summary]\
{result.text[:4000]}\")
    return [*system, summary, *recent]

The summary instruction is specific. It tells the model to preserve the task, the key decisions and why they were made, the discoveries including failed approaches, and the next steps. The system prompt is never compacted, because it is essential. This keeps a long exploration inside the window without throwing away the facts that matter. It is worth noticing that this in-context compaction is a smaller, faster cousin of the durable state in git. The git saved state survives across cycles and crashes, while compaction just keeps one long cycle tidy.

The Model Layer

The cycle calls self._model.complete(...), but it never cares which model that is. That indirection is on purpose. The whole system talks to exactly one interface, and we can swap the actual model behind it with a single config change. This is what lets the same code run for zero dollars on a local model in a test, and on Claude in production.

One Interface, Many Backends

The interface is a small Protocol. A model takes a list of messages and returns a real result with real token usage. That is it.

One ModelProvider interface with swappable stub, ollama, openai, and claude backends (Created by Fareed Khan)
# src/lra/contracts/model.py

@runtime_checkable
class ModelProvider(Protocol):
    \"\"\"A pluggable LLM backend. Implementations live in src/lra/model/.\"\"\"

    name: str

    async def complete(self, messages, *, tools=None, max_tokens=None) -> \"TurnResult\":
        \"\"\"Run one real model turn and return its real output + usage.\"\"\"
        ...

    def estimate_cost_usd(self, usage: \"Usage\") -> float:
        \"\"\"Compute real USD cost from real token counts (0.0 for local/free backends).\"\"\"
        ...


class Usage(BaseModel):
    \"\"\"Real token accounting as reported by the provider.\"\"\"

    input_tokens: int = 0
    output_tokens: int = 0
    cache_read_input_tokens: int = 0
    cache_creation_input_tokens: int = 0
    model: str = \"\"

There are four implementations of this interface. The stub model is deterministic and free, and it is used in tests so the whole system can be exercised without a network or a key. The ollama and openai_compat backends talk to local or free tier cloud models. The claude backend talks to Anthropic’s Messages API. They all return the same TurnResult with a real Usage, so the rest of the system never knows the difference. The Claude backend even reports prompt cache tokens separately, which matters a lot for cost over a long run.

Real Tokens, Real Cost

Every model turn returns a real token count, and we turn that into a real dollar figure and append it to a ledger. The key point is that this number is real. We never estimate or fake the cost. We read it from the provider’s own response. The ledger is tiny.

Press enter or click to view image in full size
Every turn records real token usage into a cost ledger the governor reads (Created by Fareed Khan)
# src/lra/governor/cost.py

class CostLedger(BaseModel):
    entries: list[CostEntry] = Field(default_factory=list)

    def record(self, *, cycle_id: str, usage: Usage, usd: float) -> CostEntry:
        entry = CostEntry(
            cycle_id=cycle_id, model=usage.model,
            input_tokens=usage.input_tokens, output_tokens=usage.output_tokens, usd=usd,
        )
        self.entries.append(entry)
        return entry

    @property
    def total_usd(self) -> float:
        return sum(e.usd for e in self.entries)

    def mean_usd_per_cycle(self) -> float:
        cycles = {e.cycle_id for e in self.entries}
        return self.total_usd / len(cycles) if cycles else 0.0

The ledger keeps a running total and a mean cost per cycle. That mean is what lets the budget governor predict the cost of the next step before it runs. Local and free backends record a genuine zero, while still tracking tokens, so the cost machinery is exercised even in a free run. Failover

A week is long enough that one provider will have a bad moment. So we can wrap several providers in a FailoverModel. It tries them in order and returns the first success. Only if every provider fails does it raise.

There is also an operational mode where, if every model is hard down, the task parks itself in a durable sleep and alerts a human instead of burning retries. We will see that durable sleep soon.

Tools and the Sandbox

The model cannot touch the world directly. It can only ask for a tool to be run, and every such request passes through a single gate. That gate is where all the safety lives, and it sits in code below the model, not in a prompt that a clever input could talk its way around.

The Allow-List Dispatcher

The AllowListDispatcher is the one and only path from a model’s request to a real action. It checks four things before it runs anything. Is the tool known, is it on the allow list, is mutation allowed if this tool mutates, and is egress allowed if this tool reaches the network. Egress is default deny.

Press enter or click to view image in full size
Every tool call passes the allow-list dispatcher before it can run (Created by Fareed Khan)
# src/lra/execution/dispatcher.py

async def dispatch(self, call: ToolCall, ctx: ToolContext) -> ToolResult:
    tool = self._tools.get(call.name)
    if tool is None:
        return ToolResult.failure(f\"unknown tool: {call.name!r}\")
    if not self._permitted(call.name):
        return ToolResult.failure(f\"tool not allowed: {call.name!r}\")
    if tool.spec.mutating and not self._allow_mutating:
        return ToolResult.failure(f\"mutating tools are disabled: {call.name!r}\")
    if tool.spec.egress and not self._allow_egress:
        return ToolResult.failure(f\"egress is disabled (default-deny): {call.name!r}\")

    missing = _missing_required(tool.spec.parameters, call.arguments)
    if missing:
        return ToolResult.failure(f\"missing required args for {call.name!r}: {sorted(missing)}\")

    try:
        return await tool.run(call.arguments, ctx)
    except Exception as exc:  # a tool failure must NEVER crash the agent loop
        return ToolResult.failure(f\"{type(exc).__name__}: {exc}\")

There are two things I want to point out. First, the gate is enforced in code, below the model. A prompt injection cannot grant itself a tool, because the model is never even told a forbidden tool exists. Second, the final try/except means a tool that throws does not crash the cycle. It returns a failure result that becomes an observation, and the model gets to react to it. The loop is unbreakable from the tool side. Different roles get different dispatchers, so a read-only researcher literally cannot be handed a mutating tool.

Tools that run commands do not run on the host. They run inside a sandbox, which is just another interface with three implementations. A local subprocess sandbox for development, a Docker sandbox for CI, and an E2B micro VM sandbox for production. The agent loop talks to the interface and never knows which one is underneath.

For that we need the gate that decides what counts as done.

Deterministic Verification

This is the most important section in the blog, so I want to slow down. Over thousands of steps, small errors compound. If each step is ninety nine percent reliable, then after a few hundred steps you are almost certainly broken. The only way to stop this compounding is to never trust the model’s own claim that something works. We trust a real test instead.

The Exit Code Decides

The DeterministicVerifier runs each check as a real subprocess and looks at its exit code. An item is done only when every gating check exits zero. Not when the model says so. When the exit code says so.

Press enter or click to view image in full size
Only real exit codes, not the model’s opinion, can flip an item to done (Created by Fareed Khan)
# src/lra/verify/verifier.py

class DeterministicVerifier:
    async def verify(self, workdir: str, checks: list[Check]) -> VerificationResult:
        results: list[CheckResult] = []
        for check in checks:
            outcome = await run_proc(check.command, cwd=workdir, timeout_s=self._timeout)
            results.append(
                CheckResult(name=check.name, passed=outcome.ok, exit_code=outcome.exit_code)
            )
        # The gate: EVERY gating check must pass. Advisory checks are recorded, not gating.
        all_green = all(
            result.passed
            for check, result in zip(checks, results, strict=True)
            if check.gating
        )
        return VerificationResult(all_green=all_green, results=results)

The default gate for a Python project is three real commands, and you have seen them in the trace already.

Trusting the Gate

There is a subtle trap here. Green only means correct if the tests actually exercise the code. A repo with no tests is green and also worthless. So before we lean hard on the gate, and especially before we let parallel writers loose, we measure how much we can trust it. We use two numbers, coverage and mutation score.

Flaky Quarantine

One last verification problem. A flaky test, one that passes and fails at random, poisons the gate. If a flaky check can block progress, then green becomes unreliable and the agent wastes cycles chasing ghosts. So we quarantine known flaky checks. They still run, for visibility, but they are forced to be non-gating.

Press enter or click to view image in full size
Flaky checks still run for visibility but are forced non-gating (Created by Fareed Khan)
# src/lra/verify/flaky_quarantine.py

class FlakyQuarantine:
    def __init__(self) -> None:
        self._flaky: set[str] = set()

    def mark_flaky(self, name: str) -> None:
        self._flaky.add(name)

    def partition(self, checks: list[Check]) -> tuple[list[Check], list[Check]]:
        \"\"\"Split into (gating, quarantined); quarantined checks are forced non-gating.\"\"\"
        gating, quarantined = [], []
        for check in checks:
            if check.name in self._flaky:
                quarantined.append(check.model_copy(update={\"gating\": False}))
            else:
                gating.append(check)
        return gating, quarantined

A quarantined check is copied with gating=False, so it can never block an item, but it still runs so we can track its flake rate over time. This keeps the meaning of green clean. We now have a complete inner engine. It reads truth, acts through gated tools in a sandbox, and only marks progress when a trustworthy test passes. The next problem is making that engine survive for a week.

The Durable Backbone

The inner loop is good, but on its own it is still just a Python process. If that process dies, the loop dies with it. To run for a week, we wrap the loop in a durable execution engine. We use Temporal. The idea of Temporal is that your control flow is split into two kinds of code. There is workflow code, which must be deterministic and is journaled so it can be replayed, and there is activity code, which does all the messy non deterministic work and whose results are recorded once and then served from a cache on replay. This split is what gives us crash recovery for free.

The Deterministic Scheduler

The MissionWorkflow is the scheduler, and it is deliberately tiny and boring. It contains no model calls, no file IO, and no randomness. All it does is dispatch one cycle activity at a time and count how many have run.

Press enter or click to view image in full size
The MissionWorkflow is a deterministic scheduler that dispatches one activity per cycle (Created by Fareed Khan)
# src/lra/durable/workflows.py

@workflow.defn
class MissionWorkflow:
    @workflow.run
    async def run(self, inp: MissionInput, state: MissionState | None = None) -> MissionResult:
        state = state or MissionState()
        self._cycles_done = state.cycles_done

        while True:
            if state.cycles_done >= inp.max_cycles:
                return await self._terminal(inp, state, completed=False)

            # The ONE activity per loop. All real work happens inside it.
            result = await workflow.execute_activity(
                run_agent_cycle,
                CycleInput(
                    mission_id=inp.mission_id, workdir=inp.workdir,
                    cycle_id=f\"c{state.cycles_done + 1}\", check_commands=inp.check_commands,
                ),
                start_to_close_timeout=timedelta(minutes=10),
                retry_policy=_CYCLE_RETRY,           # up to 10 tries, exponential backoff
            )
            state.cycles_done += 1
            self._cycles_done = state.cycles_done

            if result.is_complete:
                return MissionResult(mission_id=inp.mission_id, completed=True,
                                     cycles=state.cycles_done, head_sha=result.head_sha,
                                     items_done=result.items_done, items_total=result.items_total)

            if state.cycles_done % inp.cycles_before_can == 0:
                workflow.continue_as_new(args=[inp, state])    # bound history (see below)

That is the entire scheduler. Read it and notice what is not there. There is no business logic. The workflow only decides when to run the next cycle and when to stop. Because the workflow is deterministic, Temporal can replay its history at any time and arrive at the exact same state. The retry policy means that if a cycle activity fails, Temporal retries it up to ten times with backoff before giving up. The real intelligence is all inside that one activity.

The activity is where everything non deterministic lives. It runs the real AgentLoop we built earlier. The crucial property is that it is idempotent. It always reads fresh state from git and advances the next actionable item, so running it twice is safe.

Durable Sleep and Continue-As-New

Two more tricks make the week long part actually work. The first is durable sleep. When there is nothing to do, for example overnight, the workflow sleeps on a durable timer. This costs nothing and survives reboots. The second is Continue-As-New. A week long run would otherwise pile up a gigantic event history, so every so many cycles the workflow rolls over into a fresh execution, carrying only a tiny compact state.

The Claim-Check Codec

Over a week, the workflow journals thousands of steps, and some payloads are large, like a big model response or a long test log. If we journaled those raw, Temporal’s history would balloon. So we use the claim-check pattern. Any payload over a threshold is stored in an object store, and only a short content addressed key goes into the journal.

Press enter or click to view image in full size
Large payloads go to an object store and only a short key is journaled (Created by Fareed Khan)
# src/lra/durable/codec.py

class ClaimCheckCodec(PayloadCodec):
    async def encode(self, payloads):
        encoded = []
        for payload in payloads:
            if len(payload.data) > self._threshold:        # default 32 KiB
                key = await self._store.put(payload.data)   # store the bytes...
                encoded.append(Payload(
                    metadata={\"encoding\": _CLAIMCHECK_ENCODING,
                              \"lra-orig-encoding\": payload.metadata.get(\"encoding\", b\"\")},
                    data=key.encode(\"utf-8\"),               # ...journal only the key
                ))
            else:
                encoded.append(payload)
        return encoded

The object store keys are SHA256 hashes of the content, so identical payloads are stored once automatically. A ten megabyte response becomes a sixty four character hash in the history. You can see this in the very first line of the trace, where the data converter is configured with a claim-check threshold.

#### OUTPUT ####
09:00:01 INFO  temporal.connect addr=localhost:7233 ns=default build_id=lra-7f1c
               data_converter=ClaimCheckCodec(threshold=32768)

The codec is wired in at the data converter level, so the activity code never knows it is happening. It just passes objects around, and large ones are transparently offloaded. This is what keeps the journal small enough to replay quickly even after a week of work.

Sagas and Compensation

The last durability piece is for actions that reach outside our git repo, like creating a branch, opening a pull request, or merging. These are multi step, and a failure halfway through leaves a mess. So each forward step registers an undo action before it runs, and on failure we run the undos in reverse order.

Press enter or click to view image in full size
Each forward step registers an undo; on failure they run newest-first (Created by Fareed Khan)
# src/lra/durable/saga.py

class Saga:
    def add(self, name: str, undo: Callable[[], Awaitable[None]]) -> None:
        self._compensations.append(Compensation(name=name, undo=undo))

    async def compensate(self) -> list[str]:
        \"\"\"Run compensations newest-first (LIFO); record any undo failures, never stop.\"\"\"
        ran = []
        for comp in reversed(self._compensations):
            try:
                await comp.undo()
                ran.append(comp.name)
            except Exception as exc:
                self.failures.append(f\"{comp.name}: {type(exc).__name__}: {exc}\")
        return ran

So if we create a branch and open a pull request and then the merge fails, the saga closes the pull request and deletes the branch, in that order. One caveat. A truly irreversible action, like a production deploy, is not pretend rolled back. Instead it routes to a human gate, which we will cover soon. With the durable backbone in place, our single agent can now run for weeks. The next question is whether one agent is even the right shape.

The Uneven Team

Up to now there has been one agent doing everything. The obvious next idea is to throw a swarm of agents at the problem. I want to push back on that, because more agents is not automatically better. More agents is a cost, and we should only pay it where it actually buys something.

Why Multi-Agent Is a Cost

When several agents write code at the same time, they make conflicting assumptions, they step on each other’s files, and the design loses coherence. Parallelism helps for work that is genuinely independent, like reading different parts of a codebase or reviewing finished work with fresh eyes. It hurts for coupled writing, where every decision depends on the last. So the team is uneven on purpose.

Press enter or click to view image in full size
One lead writes; researchers and a reviewer fan out only for independent work (Created by Fareed Khan)

The shape is this. One single threaded lead engineer owns all the coupled code writing, so design decisions stay coherent. Ephemeral helpers fan out only for the two things that truly parallelize. Researchers read in parallel, and a reviewer checks the work with a fresh context. A separate integrator is the only one allowed to write to the main branch. This is not a swarm. It is a small, deliberate team where the expensive part, coherent writing, stays serial.

Every role is described by a small spec that says which model tier it uses and what it is allowed to do. This is where cost discipline lives. We spend the expensive Opus model only on high leverage judgment, and we use cheap models for bulk search.

The researcher uses Haiku, because reading and summarizing is cheap and runs many times.

This makes the cost of the whole team proportional to the value of the decision, not to the amount of computation. A researcher that runs fifty times costs almost nothing, while the lead that makes the coherent design choices gets the model that is worth paying for.

Single-Writer-Per-File Ownership

When we do allow parallel implementers, we prevent collisions with one simple invariant. Every file has exactly one writer. The planner assigns files to writers, and certain shared files, like build manifests and __init__.py, can only ever belong to the lead.

Press enter or click to view image in full size
Every file has one writer; shared files always belong to the lead (Created by Fareed Khan)
# src/lra/coordination/ownership.py

class FileOwnershipMap(BaseModel):
    owners: dict[str, str] = Field(default_factory=dict)   # path -> writer id

    def permits(self, *, writer: str, path: str) -> bool:
        \"\"\"Whether `writer` may write `path` under the single-writer-per-file invariant.\"\"\"
        norm = _normalize(path)
        if is_shared(norm):
            return writer == LEAD               # shared files are always the lead's
        owner = self.owners.get(norm)
        if owner is None:
            return writer == LEAD               # unassigned space belongs to the serial lead
        return writer == owner

The rule is easy to state. If a file is shared, only the lead may write it. If a file is owned, only its owner may write it. Anything unassigned defaults to the lead. This is checked at the git layer, so a stray write fails loudly instead of silently corrupting another implementer’s slice. A writer that discovers it needs a file it does not own files a lease request rather than just writing. This is how parallel writing stays safe, on the rare occasions we allow it.

Reading is the work that parallelizes beautifully, because it has no side effects. When the lead needs context, the orchestrator fans out several researchers at once, each on a different question, and collects their briefs.

The Fresh-Context Reviewer

The second thing that parallelizes is review. The trap with a single agent is author bias. The agent that wrote the code is the worst judge of it. So the reviewer is a separate agent with a fresh context. It sees only the diff and the acceptance criteria, never the lead’s reasoning or its earlier attempts.

Staying Safe and On Budget

An agent that runs for a week and can write code, run commands, and reach the network is powerful, and powerful things need guardrails. This section is about the guardrails that keep a long run from quietly burning money, spinning forever, or doing something dangerous. None of these live in a prompt. They all live in code that the model cannot talk its way around.

The Budget Governor

The first guardrail is money. The governor refuses the next cycle before it runs if the projected spend would breach the ceiling. It does not wait until you are over budget. It predicts the next step’s cost from the running average and stops in advance.

Press enter or click to view image in full size
The governor refuses the next cycle before it runs if it would breach the ceiling (Created by Fareed Khan)
# src/lra/governor/governor.py

class BudgetGovernor:
    \"\"\"Refuses the next step BEFORE it runs if it would breach the spend/iteration ceiling.\"\"\"

    def authorize_next(self, ledger, *, cycles_done, projected_usd=None) -> GovernorDecision:
        spent = ledger.total_usd
        # Estimate the next step from history if no explicit projection was given.
        estimate = projected_usd if projected_usd is not None else ledger.mean_usd_per_cycle()
        projected_total = spent + estimate

        if cycles_done >= self._max_cycles:
            return self._deny(\"max cycles reached\", projected_total, spent)
        if projected_total > self._ceiling:
            return self._deny(\"projected spend exceeds ceiling\", projected_total, spent)
        return GovernorDecision(allow=True, reason=\"within budget\",
                                projected_usd=projected_total, spent_usd=spent,
                                ceiling_usd=self._ceiling)

The agent loop calls authorize_next at the top of every cycle, and if the decision is not allow, the task stops cleanly rather than overspending. Here is the governor authorizing a cycle and then ticking the running total later in the run.

#### OUTPUT ####
07:30:01 INFO  governor.authorize cycle=c1 allow=true projected_usd=0.06 spent=0.094
...
17:48:02 INFO  governor.tick cum_usd=31.29 tests=0/1 active=01 cycles_today=1 attempts=12

The first line shows a cycle being authorized because the projected total is well under the ceiling. The second line, much later, shows the cumulative spend at 31 dollars and 29 cents after a hard day of failed attempts on the transport. The governor never had to intervene on this task, because it finished at 178 dollars against a 400 dollar ceiling, but it is the reason a stuck task cannot silently run up a thousand dollar bill.

The Loop Detector

The second guardrail is time. An agent can get stuck retrying the same failing thing over and over. The loop detector watches for the same state and action signature recurring, and after a threshold it trips and escalates.

Press enter or click to view image in full size
The loop detector trips when the same state and action repeats too often (Created by Fareed Khan)
# src/lra/governor/governor.py

class LoopDetector:
    \"\"\"Flags oscillation: the same (state, action) signature recurring too often.\"\"\"

    def __init__(self, *, threshold: int = 3) -> None:
        self._threshold = threshold
        self._counts: Counter[str] = Counter()

    def observe(self, signature: str) -> bool:
        \"\"\"Record a signature; return True once it has looped past the threshold.\"\"\"
        self._counts[signature] += 1
        return self._counts[signature] >= self._threshold

This is exactly what saved the LSP task from grinding forever on the transport. After the same kind of edit kept failing, the detector first warned, then tripped, and the work was escalated to the reviewer we met earlier.

#### OUTPUT ####

...
10:15:09 ERROR loop_detector signature=\"01:transport:rewrite\" count=4 action=TRIP
10:15:09 INFO  orchestrator.pause item=01 ; escalate=reviewer reason=loop-trip

The signature 01:transport:rewrite recurred four times, the detector tripped, and instead of letting the lead keep failing, the orchestrator paused the item and called in the reviewer. That escalation is what produced the architecture finding that unstuck everything. The loop detector did not fix the bug. It noticed that the agent could not fix it alone, and asked for help.

Default-Deny Egress

Now the dangerous part, the network. The egress policy is default deny. No host is reachable unless it is explicitly on an allow list. And the agent never holds real credentials. It only ever sees placeholders, and a broker swaps in the real secret at the very last moment, at the egress boundary.

Press enter or click to view image in full size
Egress is default-deny and a broker injects real secrets only at the boundary (Created by Fareed Khan)
# src/lra/safety/egress.py

class EgressPolicy(BaseModel):
    \"\"\"Allow-list of permitted egress hosts (default-deny: empty = nothing allowed).\"\"\"

    allow_hosts: set[str] = Field(default_factory=set)

    def permits(self, url: str) -> bool:
        host = urlparse(url).hostname
        return host is not None and host in self.allow_hosts


class CredentialBroker:
    \"\"\"Maps placeholder tokens to real secrets, injected only at egress.\"\"\"

    def resolve(self, value: str) -> str:
        for placeholder, secret in self._secrets.items():
            value = value.replace(placeholder, secret)   # swap at the boundary only
        return value

The benefit is concrete. If the agent is somehow hijacked by a malicious web page it reads, the worst it can leak is a useless placeholder string, because the real secret never enters its context. And it can only reach hosts we approved. In the trace, every fetch records the egress decision next to it.

#### OUTPUT ####
09:00:12 INFO  tool.exec agent=researcher-1 name=web_fetch
               url=microsoft.github.io/.../specification/#headerPart -> 200 egress=allow(microsoft.github.io)

The fetch succeeded and the log shows egress=allow(microsoft.github.io), which means that host was on the allow list. A request to any host not on the list would have been refused by the policy before it ever left the machine. Network access is a privilege the agent is granted narrowly, not a default it has.

The Rule of Two

There is a deeper safety idea here, and it is structural rather than a single check. Meta named it the rule of two. There are three dangerous capabilities. Ingesting untrusted content, having access to private data, and being able to communicate externally. Holding all three at once is the dangerous combination that makes prompt injection catastrophic. So a single session is allowed at most two of the three.

Press enter or click to view image in full size
A session may hold at most two of untrusted content, private data, and external comms (Created by Fareed Khan)
# src/lra/safety/rule_of_two.py

class Capability(str, Enum):
    UNTRUSTED_CONTENT = \"untrusted_content\"   # web pages, issue text, ...
    PRIVATE_DATA = \"private_data\"             # secrets, customer data
    EXTERNAL_COMMS = \"external_comms\"         # egress / side effects


def check_rule_of_two(capabilities: set[Capability]) -> None:
    \"\"\"Raise if a session would hold the full lethal trifecta (all three at once).\"\"\"
    if len(capabilities) >= 3:
        raise RuleOfTwoViolation(
            \"session would hold untrusted content + private data + external comms \"
            \"(the lethal trifecta); split capabilities across sessions\"
        )

The orchestrator checks this before it grants a session its capabilities. If a piece of work would need all three, it is split across separate sessions instead. You saw the proof for this in the research fan-out trace, where the line read rule_of_two=ok caps=2. The researchers could read untrusted web content and reach the network, which is two capabilities, but they had no access to private data. The system enforced the limit before letting them run. This is safety by structure, not by hoping the model behaves.

Human-in-the-Loop Gates

Some actions are too risky to ever take automatically, like merging to a protected branch or deploying. For those, the system pauses and asks a human. The gate is durable, so it can wait for days at zero cost, and crucially it has a timeout with a default action, so an absent human never makes the task hang forever.

Irreversible actions pause on a durable gate with a timeout and a default action (Created by Fareed Khan)
# src/lra/hitl/gate.py

class AutoPolicyGate:
    \"\"\"Resolves gates by policy alone (no human).\"\"\"

    async def request(self, req: GateRequest) -> GateResolution:

            return GateResolution(gate_id=req.gate_id, decision=GateDecision.APPROVE,

The durable version of this gate lives in the workflow itself, using a signal. When a human is needed, the workflow sets its status to WAITING_ON_HUMAN and parks on a condition until someone signals a decision or the timeout fires. A representative status query looks like this.

Memory That Survives Weeks

We have a system that runs for a week and stays safe. But there is a difference between surviving a week and learning over a week. The saved state gives the agent perfect recall of the current task. Memory gives it something more, the ability to carry lessons across cycles, and eventually across tasks. This is where the system stops just executing and starts improving.

Three Tiers of Memory

We split memory into three tiers, borrowed from how people talk about memory. Episodic memory is what happened, the raw event log. Semantic memory is distilled facts about the code and the domain. Procedural memory is reusable skills, actual verified code with the conditions under which it applies.

Memory has three tiers: episodic events, semantic facts, and procedural skills (Created by Fareed Khan)
# src/lra/contracts/memory.py

@runtime_checkable

    async def add(self, records: list[MemoryRecord]) -> None: ...
    async def query(self, text: str, *, k: int = 5) -> list[\"RetrievalHit\"]: ...

Notice the valid flag and the embedding_model and embedding_version fields. The valid flag means we never delete a memory outright, we only mark it invalid, which we will come back to. The model and version fields are there to stop a subtle long run bug, comparing vectors that were made by different embedding models. Over weeks, you might change your embedder, and silently mixing vectors from two models gives you garbage retrieval.

Embeddings

To search memory by meaning, we turn text into vectors. The embedder is, of course, another swappable interface. There is a real one that calls a paid semantic API, and a deterministic offline one that costs nothing and is used for tests and local runs.

Press enter or click to view image in full size
Embeddings come from a swappable embedder, with an offline hash version for $0 runs (Created by Fareed Khan)
# src/lra/memory/embeddings.py

class HashEmbedder:
    \"\"\"A deterministic, offline embedder (lexical hashing). For dev/CI/offline only.\"\"\"

    def __init__(self, dim: int = 256) -> None:
        self.name, self.version, self.dim = \"hash\", \"1\", dim

    async def embed(self, texts: list[str]) -> list[list[float]]:
        return [self._embed_one(text) for text in texts]

    def _embed_one(self, text: str) -> list[float]:
        vec = [0.0] * self.dim
        for token in _TOKEN.findall(text.lower()):
            bucket = int(hashlib.sha1(token.encode(\"utf-8\")).hexdigest(), 16) % self.dim
            vec[bucket] += 1.0                       # hash each token into a bucket
        norm = math.sqrt(sum(v * v for v in vec)) or 1.0
        return [v / norm for v in vec]               # normalize to unit length

The hash embedder is not semantic, it is just lexical hashing, but it is deterministic and free, so the entire memory subsystem can run and be tested with no network and no key. In production you swap in the real Voyage embedder behind the same interface. The point, as always, is that the rest of the system does not change.

Hybrid Retrieval

Pure vector search misses exact keyword matches, and pure keyword search misses meaning. So we run both and fuse the rankings. We combine a dense semantic search with a lexical BM25 search using reciprocal rank fusion, which blends two ranked lists without needing their scores to be on the same scale.

Press enter or click to view image in full size
Dense and lexical search are fused with reciprocal rank fusion, then reranked (Created by Fareed Khan)
# src/lra/memory/hybrid.py

def reciprocal_rank_fusion(rankings: list[list[str]], *, k: int = 60) -> list[tuple[str, float]]:
    \"\"\"Fuse ranked id-lists via RRF: score = sum of 1/(k + rank).\"\"\"
    fused: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(fused.items(), key=lambda pair: pair[1], reverse=True)


class HybridRetriever:
    async def query(self, text: str, *, k: int = 5, candidate_k: int = 20) -> list[RetrievalHit]:
        dense = [h.record.id for h in await self._semantic.query(text, k=candidate_k)]
        lexical = [doc_id for doc_id, _ in self._bm25.query(text, k=candidate_k)]
        fused = reciprocal_rank_fusion([dense, lexical])     # blend both rankings
        # ... map ids back to records and return the top k ...

The fusion is elegant. Each list contributes a score of one over a constant plus the rank, so an item that both methods rank highly floats to the top, while an item only one method found still gets a fair shot. This is the standard two stage retrieval recipe, and it is all pure Python, so it runs at zero cost and is fully deterministic. There is also an optional cross encoder reranker for the final polish, but the noop reranker is the free default.

The highest tier is procedural memory, an actual library of reusable skills. A skill is code plus the preconditions under which it applies. The critical rule is that a skill is admitted into the library only if it was verified, meaning it passed the deterministic test gate when it was learned.

Making the Lesson Permanent

The memory we just built helps within a task. But the most interesting kind of learning happens between tasks. After a task ends, the system can look back at its failures and improve its own prompts, so the next task of the same kind goes better. This is self improvement, and it is done very carefully, because letting an agent rewrite its own instructions is dangerous if you do it naively.

Proposing a Better Prompt

The first step happens entirely offline, between tasks, never on a live run. An evolver reads the failure traces from a finished task and proposes an improved system prompt for a role. This is a reflective optimization, in the spirit of GEPA. Importantly, the output is only a candidate. Nothing is changed yet.

The Eval Harness and the Judge

To decide whether a candidate prompt is actually better, we run it against a held out set of gold cases and score the results. The scoring uses an independent agent as a judge, with a rubric, because many of these criteria are fuzzy and not a simple pass or fail.

22:14:55 INFO  eval.run set=wire-protocol-gold n=20 baseline=0.71 candidate=0.85

On twenty gold cases, the baseline prompt scored 0.71 and the evolved prompt scored 0.85. The judge recommends promotion, a gain of 0.14 with zero regressions. Now the candidate has evidence behind it. But we still do not just ship it.

The Promotion Gate

The final gate is the strictest. A candidate is promoted only if it beats the baseline on the evals, and it also has to pass a replay against recorded task histories so we know it does not break determinism, and even then it goes out as a pull request that a human approves. A live agent’s prompt is never hot patched.

Press enter or click to view image in full size
A candidate is promoted only after evals, a clean replay, and human approval (Created by Fareed Khan)
# src/lra/agents/evolution.py

async def evolve_and_gate(*, model, role, current_prompt, failure_traces,
                          baseline_cases, candidate_cases, min_improvement=0.0) -> EvolutionResult:
    \"\"\"Propose an improved prompt and promote it ONLY if it beats baseline by min_improvement.\"\"\"
    candidate = await PromptEvolver(model).propose(
        role=role, current_prompt=current_prompt, failure_traces=failure_traces)
    baseline = await run_eval_suite(model=model, cases=baseline_cases)
    evolved = await run_eval_suite(model=model, cases=candidate_cases)
    promoted = evolved.pass_rate >= baseline.pass_rate + min_improvement
    return EvolutionResult(promoted=promoted, candidate=candidate,
                           baseline_pass_rate=baseline.pass_rate,
                           candidate_pass_rate=evolved.pass_rate,
                           reason=(\"candidate improved\" if promoted else \"rejected\"))

The gate is a chain of independent checks, the evals, the judge, and a replay. Here is the final promotion step from the trace.

#### OUTPUT ####
22:15:31 INFO  replay.histories n=9 result=9/9 clean
22:15:31 INFO  evolve.promote target=prompts/lead.md mode=PR human_approval=required (never hot-patched a live run)

Nine recorded histories replayed cleanly against the new prompt, and only then was the change promoted, as a pull request, with human approval required. The phrase at the end of that line is the whole safety philosophy of self improvement. The system never hot patches a live run. It proposes, it proves, it asks, and only then does the improvement land. The next wire protocol task will skip most of the multi day wasted effort, because the lesson is now baked into the lead’s standing instructions. The loop paid for itself.

A Week in the Life of a Task

We have built every component. Now let us watch them work together over a full week, on the one task I have been quoting from. The task is to build a small Python language server from scratch. A language server speaks a specific wire protocol over standard input and output, which turns out to be a surprisingly nasty little problem. This section is the whole run, start to finish, so you can see how the pieces we built actually behave under real pressure.

Day Zero: Research and Plan

The task starts with a single command. The workflow spins up, the saved state is initialized, and the governor reads its ceiling. Then, instead of guessing at the protocol, the lead does the smart thing and spends its first move on research.

The Hard Part

The transport is the first item, and it is brutal. The lead writes a transport, runs the test, and it fails. It tries again, and it fails differently. Over a full day it makes twelve attempts, each one fixing the last symptom and exposing a new one. Bare JSON with no header, then a two byte mismatch from Windows newline translation, then a short read on the pipe, then an asyncio deadlock.

Crash and Replay

On day three, while the transport is still red, the host machine reboots for an OS update, right in the middle of a cycle. This is the disaster that kills a normal agent. Here it is a non event.

The worker died and a new one came up. Temporal replayed the journal, served the completed work from cache, and the task continued from the exact cycle it was on. No tokens were re-spent and no commits were duplicated. And notice it restored a still failing transport, because that was the real state. The durable backbone protected the work without pretending the bug was fixed. The task was stuck before the crash, and it is stuck after the crash, which is exactly correct.

Getting Unstuck

What finally breaks the deadlock is not a lucky edit. It is the loop detector tripping, which escalates to the reviewer, which produces the architecture finding we saw earlier. Overnight, the librarian consolidates the failures into lessons. The next morning the planner re-plans with those lessons in context, cuts the scope, and the lead rebuilds the transport as an isolated, tested unit.

What Is Proven vs Frontier

It is worth being clear about what this system is and is not, because it is easy to oversell an agent demo. So here is the clean split.

The following parts are proven and tested. They are engineering, and they work today.

Durability and crash recovery. A reboot mid run loses no work and re-spends no tokens.
State lives outside the model. It is kept in git, so any restart rebuilds the picture in seconds.
Deterministic verification. Real tests, not the model’s opinion, gate every piece of progress.
The safety boundaries. The tool gate, default deny egress, the budget governor, and the loop detector are all enforced in code.
Tiered memory and skill reuse, with skills admitted only after they pass the gate.

And here is the frontier, the part I will not overclaim. Fully hands off, multi week autonomy where a model reliably drives complex work for days without any human is not a solved problem, and no model today does it reliably. The task horizons we can trust are still well under a day at high reliability.

Press enter or click to view image in full size
What is proven and tested versus what is still the frontier (Created by Fareed Khan)

So the claim of this system is precise. The system runs for weeks. It sleeps, it survives, it resumes, and it never loses track of what it is doing, because durability and verification are engineering properties of the system, not capabilities we are hoping the model has. The model drives the work in short, verified bursts, with human gates on the irreversible actions. That framing is the title of this blog. Durability is an engineering property, not a model capability. We did not make the model smarter. We built a system that lets a model of today do a week of careful work without falling apart.

What’s Next

If you want to build on this, I would start small and earn each layer. Get the git saved state and the single cycle loop working first, with the deterministic verifier as your gate, and prove to yourself that a crash mid run loses nothing. That durable single agent backbone is the hard, valuable core, and everything else is an addition that only earns its place where it provably helps. Add the reviewer when author bias starts costing you. Add the researchers when reading is your bottleneck. Add memory and self improvement when you are running the same kind of task again and again.
